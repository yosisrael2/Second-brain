Second Brain MVP — how it works

A guided tour of the running code on feature/mvp-dev-providers (commit b22a3b0). Every claim links to the file and line that implements it.

Jev decides, LLMs write, the DB remembers. Jev (the TypeSafe decision API, ai/jev.py:123, default model jev-latest) makes the judgment calls — what an item is, how confident the classification is, which search candidates matter. Claude writes the answers, in a tool-less sandbox with no access to your machine. Postgres is the source of truth: vectors are an accelerant, never the record.

1 · What this is, in one paragraph

Second Brain is a personal knowledge capture service. You POST pieces of text (a note, a decision, a task) to POST /items; Jev classifies each one (type, importance, actionability, confidence) and routes it into an inbox / review / filed workflow. Everything is stored in Postgres and embedded into Qdrant so you can later search semantically (GET /search) or ask questions over your own knowledge (POST /ask), with answers that cite the stored items they used. The interesting engineering property is graceful degradation: every AI component can be down (no API keys, network down, service restarting) and the core loop — capture, store, keyword-search — keeps working.

2 · Component map

Thin HTTP routers call framework-free services; services own the business logic and talk to two kinds of collaborators: repositories (Postgres, via SQLAlchemy) and the AI layer (Jev, embedders, vector store, LLM clients).

3 · Flow: capture (POST /items)

The write to Postgres happens first (ingest.py:61); classification and embedding run after, and their failures are logged but never fail the request.

4 · Flow: semantic search (GET /search)

9 · Security model of /ask

Captured text is untrusted input that reaches an LLM. ClaudeSdkLLMClient (ai/claude_sdk.py:102-107) runs every session with the model's capabilities removed, not merely restricted:

  • tools=[] — the CLI is invoked with --tools '': no tools exist at all. (allowed_tools=[] would be a no-op — it only auto-approves tools that already exist; claude_sdk.py:47-48.)
  • setting_sources=[] — user and project settings files are never loaded, so no repo file can grant permissions (claude_sdk.py:49-51).
  • strict_mcp_config=True — no project .mcp.json server discovery (claude_sdk.py:51).
  • Each session gets a fresh scratch working directory (brain-ask-*, tempfile.mkdtemp, claude_sdk.py:74), deleted on close — it never runs in this repository.
  • max_turns=1 — one prompt, one answer, no agentic loop (claude_sdk.py:107).

What a prompt injection inside a stored item can do: influence the text of the answer — that is all the model has. What it cannot do: execute commands, read files, load settings, or persist anything. Verified empirically: the spawned CLI session reports an empty tool list at startup, and adversarial items instructing the model to "use the Bash tool" produced only plain text — no tool call, no side effects.

10 · Run it locally

  1. docker compose up -d — Postgres 16 + Qdrant with health checks (docker-compose.yml).
  2. pip install -e ".[dev]"; copy .env.example → .env.
  3. alembic upgrade head — create the schema.
  4. uvicorn brain.main:app --reload; check GET /health.
  5. Capture: curl -X POST :8000/items -H 'Content-Type: application/json' -d '{"raw_text": "…"}'
  6. After bulk imports or outages: brain reindex.
